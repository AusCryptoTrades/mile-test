# Batch 89 onboarding release

## Data ownership

- Supabase Auth verifies email. The existing invitation RPC still validates and redeems invitations. Membership owns the onboarding stage, revision and completion timestamp. Existing memberships and their profile and training records are preserved.
- `mile_profiles` owns social identity, profile images, disciplines and social privacy. The training document owns private athlete measurements, benchmarks and units. Programme builders can read the same athlete profile. Garmin still owns device authorization.
- Registration asks separately for the approved [MILE Training Disclaimer](https://milefitness.com.au/disclaimer). The current version is **2026-11-26**, from website commit `db458cebe4d159c3cd44228b0f40edcd1339511f`. The source document SHA-256 is `3b8f4565ed7a16af47c421760ecc99d9304885b344f0f1679292cea9a19d01b1`. The Auth insert trigger captures the submitted version with the created Auth user and a server timestamp in a private table. Later metadata edits cannot create consent. A verified account already in flight can explicitly accept before redeeming its invite. Existing members keep their access.
- The production bucket audit found that `mile-avatars` is public and contains both avatars and profile covers. Its public route bypasses profile visibility. The [Privacy Policy](https://milefitness.com.au/privacy) already discloses that a direct link can open an avatar even for a private profile. The preparation migration adds authenticated reads that follow existing profile rules. The app keeps existing URLs and object keys, and fetches the images through Storage with the viewer's session. The same loader handles the social profile, leaderboard, main header, Run Tracker and Challenges.

## Release gates

1. Use an approved, isolated hosted environment with Auth, membership, social profiles, Storage and a Garmin preview callback. The shared Running staging project lacks the social profile table and bucket. Keep it out of this rollout.
2. Apply both SQL files below to the isolated environment. Build the draft with that project's API URL and publishable key. Complete a synthetic new registration with real email delivery and confirmation, verify the version and server timestamp as an operator, and confirm that an in-flight account without consent cannot activate until it explicitly accepts. Verify a preexisting member and its preferences.
3. In the isolated environment, verify image reads with the bucket first public and then private, including a known public URL without credentials. Verify the owner, an approved follower, a pending follower, an unrelated member and an unauthenticated viewer. Change visibility and revoke a follow, then use a fresh tab to verify the result. Check that existing avatars and covers still render in the three app shells. Exercise actual Garmin authorization, return, failure and skip with a synthetic athlete.
4. Confirm the deployed disclaimer matches the approved source and fingerprint. Confirm the public Privacy Policy statement about the public avatar bucket with the owner before cutover. Keep the legal source under its existing approval process. Verify support for any installed native beta builds before changing the bucket.

Verify unauthenticated direct URLs fail in a clean browser and the permitted viewer matrix still passes. Check public-edge cache behaviour with a known synthetic pre-cutover URL. If stale responses persist, keep the release open until expiry or an authorised provider purge is confirmed.

## Rollback

- **Before the bucket switch**: use Cloudflare Pages **Deployments → previous deployment → Rollback to this deployment**. Leave the additive SQL and receipts in place. Pause invitation redemption if the old frontend cannot collect the required disclaimer. Restore the grant only when users can accept it again.
- **After the bucket switch**: leave the bucket private and preserve existing photos, consent receipts and onboarding records. Roll back to a tested frontend deployment that includes the authenticated image loader and disclaimer flow. If no compatible deployment is ready, pause invitation redemption if affected and fix forward using the reviewed Batch 89 artifact. Reopen only after the hosted viewer matrix and registration pass. Switching the bucket back to public would reopen the direct-link exposure.
- Any later database rollback requires its own approved migration. Do not drop consent receipts or reset membership progress during a frontend rollback.

The browser tests use synthetic responses. The database CI runs both migrations against PostgreSQL and exercises invitation enforcement, receipt storage, and the Storage RLS policy. PR #138 modifies sign-out and Garmin import code in the same app file. Batch 89 is independently deployable from current main.
