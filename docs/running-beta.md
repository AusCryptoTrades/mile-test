# Two-person Running beta

## Owner setup

### On iPhone

1. Open the latest **Running beta download** check on [draft PR #140](https://github.com/AusCryptoTrades/mile-test/pull/140/checks) in Safari while signed in to GitHub. On the workflow run's **Summary**, tap the download icon next to `mile-running-beta-staging` under **Artifacts**. Safari saves the ZIP in **Files → Browse → Downloads**. Keep it zipped for Cloudflare. The artifact expires seven days after the run.
2. In Cloudflare, open **Workers & Pages → your existing non-production Pages project → Settings → General → Access policy** and enable it for previews. In **Zero Trust → Access controls → Applications**, open the generated Pages preview application and edit its allow policy to include just the two approved emails. Keep any production project separate. Verify a Private Browsing tab shows a Cloudflare Access challenge before sign-in.
3. For a **Direct Upload** Pages project, open **Deployments → Create deployment**, choose **Preview**, enter a branch name such as `running-beta`, select the ZIP in Files, and deploy. Copy the resulting HTTPS preview URL from **Deployments**. Use that one URL for both people. A Git-integrated project requires a Pages CLI upload for this prebuilt ZIP. Use `npx wrangler pages deploy ./mile-running-beta-staging --project-name <non-production-project> --branch running-beta` from a workstation after unzipping and signing in to Cloudflare. Verify `running-beta` is a preview branch before running the command.
4. Open [MILE Staging Auth URL Configuration](https://supabase.com/dashboard/project/fnyfeelynaozxtftrrga/auth/url-configuration). Set **Site URL** to the exact preview URL and add both that URL and its `/mile-reset-password.html` URL under **Redirect URLs**. In **Authentication → Providers → Email**, keep email confirmation enabled. Use the existing staging confirmation template and approved mail delivery. Supabase’s default mail service sends only to the organisation’s pre-authorised team addresses. If either recipient is ineligible, check an existing staging SMTP configuration first. An admin may instead invite each address from **Authentication → Users → Add user → Send invitation** if mail delivery is available. Use ordinary self-signup when verifying the signup confirmation flow.
5. Make the two private, inbox-bound MILE invitations using [the staging SQL](../supabase/staging/create-running-beta-invites.sql). Tap **Raw** in GitHub, copy the script into the [MILE Staging SQL Editor](https://supabase.com/dashboard/project/fnyfeelynaozxtftrrga/sql/new), replace just the two email placeholders, and tap **Run**. Send each person only their own code and the preview URL. On the phone each person signs in to Cloudflare Access, signs up in MILE, confirms the email and redeems the matching code. Then verify onboarding and private photo access using synthetic data. The Access link and the MILE invitation are separate checks.

Garmin is optional for the first walkthrough. Use **Skip for now** to test onboarding, Build, Calendar and Tracker. See [Cloudflare preview Access](https://developers.cloudflare.com/pages/configuration/preview-deployments/), [Cloudflare Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/) and [Supabase email delivery](https://supabase.com/docs/guides/auth/auth-smtp).

### Owner steps for Garmin sandbox access

1. In Garmin's developer portal, select the approved **sandbox** application. Confirm access to the Training and Activity APIs. In its OAuth redirect settings, add `https://fnyfeelynaozxtftrrga.supabase.co/functions/v1/garmin-oauth-callback`. Use a Garmin test account approved for sandbox data.
2. In [MILE Staging → Edge Function Secrets](https://supabase.com/dashboard/project/fnyfeelynaozxtftrrga/functions/secrets), set `GARMIN_CLIENT_ID` and `GARMIN_CLIENT_SECRET` to the sandbox values and `MILE_GARMIN_BETA_ORIGIN` to the exact protected HTTPS `.pages.dev` origin, with no trailing slash. Share only the preview URL and confirmation of setup in the review thread. Keep keys and inboxes in their dashboards.
3. Before anyone connects Garmin, finish the staging-only ingestion schema and deployments for `garmin-oauth-start`, `garmin-oauth-callback`, `garmin-connection-status`, `garmin-data-read` and `mile-garmin-device-sync`. Test sandbox publication and readback with a synthetic workout. Use the [controlled watch check](garmin-step-check.md) to verify the remaining physical steps. Collect the [sanitised publication and completion pair](overnight-release.md#minimum-garmin-identity-fixture) for completed-activity validation. Keep automatic matching, adaptation and republication disabled.

### Deployment and verification details

1. Use the staging-only ZIP from the PR review or build the exact reviewed commit. Unzip to a fresh directory. The ZIP uses MILE Staging `fnyfeelynaozxtftrrga` and its publishable key. Its Content Security Policy limits app network requests to staging. It contains no service credentials or account records.
2. Deploy the extracted files to an existing **non-production** Cloudflare Pages preview with access restricted to the two testers, if available. In Cloudflare, verify the selected branch is a preview branch, confirm its address in **Deployments**, and check for the staging marker and no-store response. Leave the production deployment and custom domains unchanged. A workstation can serve the same build locally using `MILE_STAGING_PUBLISHABLE_KEY=… node scripts/serve-running-staging.mjs`, which binds to loopback.
3. In MILE Staging, set Authentication → URL Configuration to the exact HTTPS preview URL and allow its `/mile-reset-password.html` redirect. Confirm signup mail delivery to the two approved inboxes using the existing MILE confirmation template. Run [create-running-beta-invites.sql](../supabase/staging/create-running-beta-invites.sql) in the staging SQL Editor with those inboxes. It binds each invitation to a verified inbox, limits it to one use and expires it in 48 hours. Call the participants **owner** and **tester** in reports. Send each preview link and invitation privately. Keep production sign-in and training exports out of staging.
4. Sign in using a new staging account in a separate browser profile or private browser. Verify email, accept the Training Disclaimer, redeem your own invitation and use the onboarding flow. Validate sign-out, sign-in resumption and a private image with a synthetic photo. The two testers should use separate staging accounts and browser sessions.
5. Scope Garmin to an approved sandbox connection. Verify the staged publication registry and provider ingestion schema, deploy the approved OAuth, reader and Device Sync Edge Functions into MILE Staging, and register `https://fnyfeelynaozxtftrrga.supabase.co/functions/v1/garmin-oauth-callback` in the Garmin sandbox and set the staging-only `GARMIN_CLIENT_ID`, `GARMIN_CLIENT_SECRET` and `MILE_GARMIN_BETA_ORIGIN` secrets. Use the exact HTTPS `.pages.dev` preview origin for `MILE_GARMIN_BETA_ORIGIN`. The staged OAuth code rejects other origins. Confirm sandbox permission and staged readback on a synthetic workout before letting the testers connect. Use a dedicated Garmin test account or a connection that is approved for staging-only data. If any Garmin prerequisite is missing, use the local FIT check or walk through Build and Calendar. Keep automatic matching, adaptation and republication disabled.
6. For any session the testers plan to perform, obtain the qualified coaching and safety review required by the release runbook. A usability walkthrough can stop at reviewing the plan. The local controlled device check can be done with gentle movement if appropriate.

The repository runner could inspect MILE Staging via its management connector. It had no Cloudflare Pages deployment access, and the staging HTTP and published legal origins were blocked by its proxy. A live, authenticated beta requires the preview and mailbox configuration in steps 2–4. Garmin end-to-end additionally requires step 5.

## Owner and tester walkthrough

| Stage | Owner | Tester |
| --- | --- | --- |
| Access | Verify disclaimer version and invitation isolation, and sign out and back in. | Verify the invitation works only on your staging account and onboarding resumes. |
| Build | Generate a modest plan from entered preferences and check an easy, long and structured session. Confirm warm-up, work, recovery and cool-down each have a purpose. | Review the plan against your own safe availability and save only if appropriate. Review alone counts. |
| Calendar and Tracker | Check one-step whole-kilometre runs, hours and minutes, zone labels and structured mixed steps. | Open a suitable session from Calendar in Tracker. Stop after inspecting it if the workout is unsuitable. |
| Garmin | With an approved sandbox, choose one appropriate scheduled workout, preview it and publish once. Compare the watch with Calendar. | Verify the distance countdown, timed transitions and lap press with the short [controlled watch check](garmin-step-check.md). Use gentle movement for HR crossing or record that the condition was unresolved. |
| Import and Analysis | In the sandbox, import the completed activity, confirm its scheduled match and check MILE IQ. Check a second device retains the link. | Read the MILE IQ brief and open **Detailed Analysis** to see charts and recorded training comparisons when data is available. Check that missing HR or unverified steps leave those comparisons unavailable. Review a recovery proposal only if an eligible check-in produces one. |

When finished, use **Settings → Connected devices → Download beta report**. The file contains only the build identifier and completed checkpoints. Add the watch model, firmware, browser and a short description of any unexpected transition separately. Crop screenshots to the workout step and omit names, emails, account/device IDs, route maps and exact timestamps. Use the runbook's sanitisation rules before supplying a publication/completion pair.

## Release and rollback

1. Preserve the verified PR head, previous staging preview, staging migration ledger and a backup. Keep the invitation window short. Validate the staging acceptance criteria in the table before inviting anyone else. The proposed migrations and staging preview are independent of a production deployment.
2. For rollback, remove access to the preview or return testers to the last verified staging preview. Let unused invitations expire or disable the two beta invitations in the staging admin UI. Disconnect only the sandbox Garmin test connection if necessary. Preserve consent receipts, photos, confirmed matches, revisions and training records. Do not run down migrations as a routine rollback.
3. Onboarding may ship independently through draft #139 after hosted email, consent, private image HTTP/cache and approved legal wording are verified. Follow the [existing release and rollback runbook](overnight-release.md) for a separately authorised production release. The Running recovery, match and device gates remain separate.
