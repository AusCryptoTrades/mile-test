# MILE private runner beta

This guide covers draft PR #146 and the Running, Cycling, Swimming, onboarding, UI and Apple stack included in its head. Start with two verified staging users. Expand to 10–15 runners after both device walkthroughs, hosted checks and independent coaching and safety review. Use a suitable easy session or stop after reviewing the workout. The beta has manual matching and evidence-gated approval. Automatic matching, adaptation and republication stay disabled.

## Owner setup on iPhone

1. Open [PR #146 checks](https://github.com/AusCryptoTrades/mile-test/pull/146/checks) in Safari while signed in. In **MILE private runner beta package → Summary → Artifacts**, tap `mile-private-runner-beta`. In Files unzip that outer download. Match `BUILD.txt` to the reviewed PR SHA. It contains a Pages ZIP, unsigned iOS web assets, the staging Apple SQL, this guide and checksums. The iOS ZIP cannot install an app.
2. In [Cloudflare](https://dash.cloudflare.com/), select the existing non-production Workers & Pages project. Enable Access on previews and restrict the allow policy to the first two approved testers. In a Direct Upload project choose **Deployments → Create deployment → Preview**, enter `private-runner-beta` and upload `mile-web-staging.zip` as-is. For a Git-integrated Pages project, a builder can deploy the extracted web ZIP to a preview branch using the existing CLI sequence. Verify the exact preview URL prompts for Cloudflare Access in a private Safari tab. [Pages preview access](https://developers.cloudflare.com/pages/configuration/preview-deployments/) · [Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/)
3. An approved staging operator follows the database sequence below. In [MILE Staging Auth URL Configuration](https://supabase.com/dashboard/project/fnyfeelynaozxtftrrga/auth/url-configuration), use the exact protected HTTPS preview as Site URL and allow it plus its `/mile-reset-password.html` route. Keep email confirmation and the existing MILE signup template enabled. Verify mail delivery before issuing the two inbox-bound [staging invitations](../supabase/staging/create-running-beta-invites.sql). Send each tester only their own invite and the preview link through a private channel. Existing production logins and exports stay out of staging. [Supabase email delivery](https://supabase.com/docs/guides/auth/auth-smtp)
4. Choose whether to include Garmin in the first walkthrough. If yes, approve an isolated Garmin sandbox, verify the staging ingestion registry and use the staged OAuth and readback functions. Register the exact staging callback and set sandbox values in [MILE Staging Edge Function secrets](https://supabase.com/dashboard/project/fnyfeelynaozxtftrrga/functions/secrets). Use the protected preview hostname as the allowed return origin. Use sandbox Garmin accounts only. [Exact Garmin setup](running-beta.md#owner-steps-for-garmin-sandbox-access)
5. Choose who will own the Apple developer account and the beta bundle ID. If the business will be the publisher, check organisation eligibility and D‑U‑N‑S requirements. On iPhone open Apple's Developer app or use the browser enrolment site with an Apple Account that has two-factor authentication. The owner approves and completes any paid enrolment separately. [Apple Developer enrolment](https://developer.apple.com/help/account/membership/program-enrollment/)

## Apple signing and TestFlight

A GitHub-hosted macOS runner can build, sign and upload. The owner can enrol and administer App Store Connect from iPhone or web. A trusted desktop with OpenSSL can prepare certificate files if no Mac is available. The script uses Xcode on GitHub's Mac. An actual iPhone and paired Apple Watch are still required to verify HealthKit and Watch behaviour. Use an eligible Xcode/iOS SDK on the runner and confirm Apple's upload requirements before the first signed run. [GitHub macOS signing](https://docs.github.com/en/actions/how-tos/deploy/deploy-to-third-party-platforms/sign-xcode-applications) · [Apple build uploads](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds/)

1. In [Certificates, Identifiers & Profiles](https://developer.apple.com/account/resources/identifiers/list), register an explicit beta bundle ID such as `au.com.milefitness.training.beta`. Enable HealthKit and HealthKit Background Delivery. Under [App Store Connect → Apps](https://appstoreconnect.apple.com/apps), create the iOS app using that ID on the same Apple team. Record the 10-character Team ID and an unused, increasing numeric build number.
2. Generate the private signing key and a CSR on a trusted workstation. With OpenSSL, use `umask 077` and `openssl req -new -newkey rsa:2048 -keyout mile-beta.key -out mile-beta.csr`. Enter a password for the private key when prompted. Upload only the CSR when creating an **Apple Distribution** certificate. Download the certificate, convert it with `openssl x509 -inform DER -in distribution.cer -out distribution.pem` and export a password-protected PKCS#12 with `openssl pkcs12 -export -inkey mile-beta.key -in distribution.pem -out mile-beta.p12`. In the Apple portal create an **App Store Connect** provisioning profile for the exact beta ID and that distribution certificate, then download it. Keep the encrypted private material in the owner's approved vault. [Distribution certificate](https://developer.apple.com/account/resources/certificates/list) · [App Store Connect provisioning profile](https://developer.apple.com/help/account/provisioning-profiles/create-an-app-store-provisioning-profile/)
3. In [repository Environments](https://github.com/AusCryptoTrades/mile-test/settings/environments), create `mile-private-testflight`. Restrict deployment to an owner-approved **protected branch** and require an independent reviewer with self-review disabled if the repository plan supports it. Approve the workflow and its scripts at the exact SHA before attaching credentials. If the environment protections cannot be enforced as intended, keep repository signing secrets empty until an owner-approved release repository or an authorised operator is available. Use environment-only values. Never paste the values into a PR, app file, chat or screenshot. Base64 is just the input encoding for a GitHub secret. [GitHub environments](https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment)
4. For signed dry runs, add these **environment variables**: `MILE_IOS_BUNDLE_ID`, `MILE_APPLE_TEAM_ID` and `MILE_NATIVE_STAGING_PUBLISHABLE_KEY`. Add these **environment secrets**: `APPLE_DISTRIBUTION_P12_BASE64`, `APPLE_DISTRIBUTION_P12_PASSWORD` and `APPLE_PROVISIONING_PROFILE_BASE64`. Base64-encode each file without line breaks, for example `openssl base64 -A -in mile-beta.p12`. Use the staging publishable key. When the owner later authorises upload, use [App Store Connect → Users and Access → Integrations](https://appstoreconnect.apple.com/access/integrations/api) to create a dedicated App Store Connect team API key with the minimum role Apple permits for uploading. Team keys can have access across the account's apps. Record and securely add `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID` and `APP_STORE_CONNECT_PRIVATE_KEY_BASE64` for that key. If its scope exceeds the owner's approved access, use an approved upload operator instead. [Apple API keys](https://developer.apple.com/help/app-store-connect/get-started/app-store-connect-api/)
5. [GitHub requires the dispatch workflow to exist in the default branch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow). This draft leaves it dormant. After separate owner authorisation for workflow admission, open [Actions → MILE private TestFlight](https://github.com/AusCryptoTrades/mile-test/actions/workflows/mile-testflight.yml), choose the protected reviewed ref, enter its exact SHA and the build number, and leave **Upload** cleared. Review the signed archive checks for bundle ID, build number and both HealthKit entitlements. The workflow keeps credentials and signed outputs on the ephemeral runner and erases them after the job.
6. For the first phone install, obtain separate approval for a signed device smoke build or a limited App Store Connect internal TestFlight release. Run the device checklist below. Before external distribution, complete App Privacy disclosures and the privacy policy, health data handling and account deletion verification, and export compliance. Then after approval dispatch with **Upload** enabled, choose a private external group in App Store Connect, submit the build for TestFlight App Review and invite by email once approved. Avoid enabling a public invite link. [TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/) · [App privacy](https://developer.apple.com/app-store/app-privacy-details/) · [Apple account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/)

## Staging migration and recovery

1. Confirm the target is [MILE Staging `fnyfeelynaozxtftrrga`](https://supabase.com/dashboard/project/fnyfeelynaozxtftrrga) and take a recoverable staging schema/data snapshot. Record the preview deployment ID, functions, grants and existing migration ledger. Verify all staging accounts and test objects are authorised. Keep project `mgixvokjlytjuypzcfzz` out of every command.
2. Compare definitions and grants, since hosted timestamps can differ. Check the existing member, invitation, private Storage and disclaimer dependencies and the Running revision, consent, legacy-ID and manual-match dependencies listed in the [staging baseline](overnight-release.md#reproducible-staging). If a genuinely missing package needs installation, follow that baseline first. Apply the remaining approved, absent revisions in dependency order: `20261127162230_running_manual_match.sql` before `20261127182846_running_whole_km_recovery.sql`, then `20261128042840_cycling_revision_consent.sql` then `20261128071000_swimming_revision_consent.sql`. Verify prior installations by their effects and do not reapply a timestamp alias.
3. If both Apple tables are absent, run the package's `mile-apple-staging.sql` as a single transaction in the [staging SQL Editor](https://supabase.com/dashboard/project/fnyfeelynaozxtftrrga/sql/new). This runs the Batch 86 device foundation followed by `20261128113000_apple_health_beta.sql` without a gap with intermediate permissions. If the exact Batch 86 foundation is already present and the Apple RPCs are absent, run only `20261128113000_apple_health_beta.sql`. If the installed schema is partial or different, stop the migration and compare it with the reviewed files. Record the source SHA, checksums and applied entries. Hosted application needs separate approval.
4. Run the rolled-back [Running checks](../supabase/staging/running-baseline.sql) and [onboarding checks](../supabase/staging/onboarding-verification.sql). Use signed-in synthetic users to verify invitation and disclaimer, avatar and cover viewer isolation, Calendar, consent, Apple import and deletion. The isolated SQL tests document expected ACLs and concurrent/stale behaviour. Verify the native WebView can reach only staging, and check previous Safari sessions and OAuth returns independently.
5. To pause a failing rollout, remove access to the preview, expire the TestFlight build or remove its group, and restore the last verified compatible preview. Keep the avatar bucket private and use a build with authenticated image reads and disclaimer acceptance. Let unused codes expire or disable only the beta codes. Pause further signed distribution, preserve support access to disconnect/delete Apple imports, record the incident and rotate affected secrets if needed. Preserve membership, consent receipts, confirmed matches, programmes and revision history. Database rollback, if required, needs a reviewed corrective migration. [Independent onboarding recovery](batch89-onboarding.md#production-release)

## Physical acceptance checklist

| Check | Apple Watch and iPhone | Garmin |
| --- | --- | --- |
| Access and isolation | Verify email and membership, sign in, kill/reopen, lock/unlock, sign out while a system prompt is open, then switch to a different synthetic MILE account. Confirm the second account gets none of the first account's Apple observations, workouts, session or Tracker view. Reopen as the first account. | Use only the approved staging sandbox. Verify OAuth success, cancel, deny, return and retry. Verify a second MILE account cannot see the first account's connection or evidence. |
| Workout delivery | Open a short suitable Calendar workout with a distance step, timed work/recovery and supported pace or HR range. Verify the exact planned date, values and order in Apple Watch Workout. Verify distance countdown and automatic transitions. Repeat the schedule request and confirm one instance. | The owner previously confirmed 11 km and an HR range reach their watch. Check step countdown, timed recovery, lap press and HR cessation separately with the [controlled Garmin workout](garmin-step-check.md). Do not force an HR crossing. |
| Import and matching | Record one short suitable workout. Try workouts-only access first, then optional categories and denied categories. Compare date/time zone, workout duration and available HR, re-sync, and confirm the chosen Calendar match. Verify recovery and route data stay on this phone and disappear from app memory on sign-out. | Import one actual sandbox completion twice. Verify one activity, confirm the Calendar match manually and compare Training Analysis. Capture the [minimum sanitised publication/completion pair](overnight-release.md#minimum-garmin-identity-fixture). Device and staging success qualify only the demonstrated capabilities. |
| Changes and deletion | With permission, test foreground refresh after a new workout. Delete only a synthetic workout in Apple Health, then confirm its imported row is removed. Test overlap review and disconnect/delete. Surface a previously matched session for explicit unlink if appropriate. | Verify stale and duplicate publication fail safely in staging. Check relinking from a second phone. Keep automatic matching, adaptation and republication off. |

For both devices, collect the build SHA, phone/watch model, OS versions, the attempted step and what appeared. Use the staging beta report where available. Crop images to the relevant controls. Omit routes, emails, identifiers, invitations, account data and raw health samples. Never use an existing customer account to test deletion.
